# ClipSoon 架构设计

## 1. 设计原则

- 本地优先：核心功能不依赖网络；SQLite 和图片文件是唯一持久数据。
- 平台隔离：全局按键、前台窗口恢复和粘贴发送都在平台适配层。
- 可测试：时钟、历史仓库、设置、快捷键输入、剪贴板和目标窗口均可替换。
- 故障降级：即使无法恢复目标窗口，选中的内容也已写入系统剪贴板。
- 面板语义：主窗口是临时命令面板，不是传统常驻主窗口。

## 2. 模块关系

```text
macOS pasteboard / pynput ───────────────┐
                                        v
Windows hotkey host ── JSON pipe ──> supervisor ──> App ──> MainWindow ──> SearchEngine
Windows clipboard host ─ manifest ─> ClipboardController ──> HistoryRepository(SQLite + PNG)
                                                    │
                                             SelectionSender
                                                    │
                     native clipboard broker <─ ACK/verify ─> ForegroundTarget + synthetic paste
Windows foreground WinEvent ──> App ──> ClipboardController ──> native text normalization

Settings ──> LaunchAtLoginManager ──> LaunchAgent (macOS) / HKCU Run (Windows)
```

`core.py` 放模型、设置和 SQLite；`search.py` 放检索；`ui.py` 放 Qt 界面；`system.py` 放主进程中的
平台适配和发送链路；`app.py` 只做依赖装配。`launcher.py` 是不导入 Qt 的最薄进程入口，先识别
`--windows-helper`，普通模式才加载 UI。Windows 另有 `windows_hotkey_host.py`、
`windows_clipboard_host.py` 两个原生宿主，以及负责启动、协议校验、心跳和重建的
`windows_workers.py`。因此 Windows 冻结入口仍只有一个 `ClipSoon.exe`，但默认 one-dir 发布包还包含
`_internal` 运行库目录；运行时是一个 UI 主进程加两个隔离
子进程；子进程在单实例锁和 QApplication 之前分派，不会递归启动完整应用。

## 3. 数据与去重

文本哈希基于 UTF-8 原文；文件哈希基于规范化绝对路径序列；图片先转换为无损 PNG 后对字节
哈希。数据库对 `content_hash` 建唯一索引。重复采集在一个事务中更新 `updated_at`、来源和
使用时间，不新增记录。

图片存入应用数据目录 `images/<sha256>.png`，数据库只记录相对文件名。删除历史后只有在
没有其他记录引用时才删除图片，避免数据库与磁盘状态分裂。

文件记录只保存规范化绝对路径，不复制源文件。启动后立即、隐藏驻留期间每 3 秒以及每次呼出
面板时，单个后台守护工作线程会异步扫描文件记录；多文件记录中任一路径明确抛出 `FileNotFoundError` 或
`NotADirectoryError` 后，还会先确认对应卷、UNC 共享或映射盘根目录可访问，再删除整条记录。
权限拒绝、断开的共享、拔出的移动盘等不确定状态保留记录，避免把临时故障误判为永久删除。
每条记录持久保存单调递增的 `revision`；扫描在数据库锁外访问
文件系统，回库后只按 `(id, kind, revision)` 比较并删除，扫描期间重新复制、使用或收藏的记录不会
被旧结果误删。发送当前文件项前由最多两个后台守护工作线程重新解析仓库中的最新 revision，GUI 线程不执行可能阻塞的
网络路径 `stat`；失效项不会写入伪造的 `CF_HDROP`，而是删除并刷新列表。

## 4. 搜索排序

仓储查询按 `updated_at` 倒序提供基础列表，内存检索先做 Unicode NFKC 和 `casefold` 归一化。
空查询只应用类型/收藏过滤并保持仓储返回顺序。有查询时，
查询的每个字符必须按原顺序出现在同一个检索字段中，否则不匹配；完全相同固定为最高分
`1,000,000`。其余得分固定为：

```text
score = 5000 × (查询长度 / 条目长度)
      + 3500 × (相邻命中对数 / 查询相邻对数)
      + 1500 × (查询长度 / 匹配路径跨度)
```

这样同为连续命中时条目越短分越高，同长度时命中越连续分越高。搜索得分不混入新近度、
频率或收藏加成；只在得分完全相同时用 `updated_at` 决胜。连续子串和不可能匹配走原生
`find` 快路径；其余情况用稀疏动态规划精确选择综合得分最高的有序匹配路径，而不是用可能
低估连续性的贪心近似。

## 5. 平台策略

macOS 全局按键继续由 `pynput` 送入纯状态机；状态机按每个按键的按下时间清理漏失的松开事件。
Windows 不观察前台应用的键盘输入，也不使用 `pynput`、Raw Input、低级键盘 hook 或
`GetAsyncKeyState` 轮询。所有 Windows 呼出快捷键都交给
`RegisterHotKey + MOD_NOREPEAT`，由操作系统向独立宿主的消息队列投递 `WM_HOTKEY`。Windows
默认组合键为 `Ctrl+Shift+Space`；旧版持久化的双修饰键或 Win32 解析器不支持的配置在应用装配时迁移并保存，设置页在
Windows 上只提供可验证的组合键录制。当前会话唯一 mutex 避免正式版与调试实例同时响应。每次触发
时宿主先快照 `GetForegroundWindow`，并用
`GetWindowThreadProcessId + GetGUIThreadInfo` 同步记录目标 HWND/TID/PID 与当时真正接收键盘输入的
`hwndFocus` 身份，再调用
`AllowSetForegroundWindow(parent_pid)` 尝试把本次输入授予的前台切换资格交给 UI，最后在
`hotkey` 协议事件中携带完整目标快照和授权结果；UI 不再在 IPC 延迟后重新猜测原目标。焦点查询
发生竞态或失败时，协议保留已验证的顶层身份、原子丢弃焦点三元组，不会混用部分陈旧的焦点身份。注册失败是
明确的配置错误；注册成功后由 Windows 持有到宿主线程退出，不存在本地 handle 仍显示健康、系统却
静默移除监听器的分裂状态。设置切换组合键时保留最近一次收到 `ready` 的配置；候选组合键若因占用
注册失败，主进程在下一轮 Qt 事件中回写旧配置并重启旧注册，避免一次无效保存永久丢失呼出入口。
若应用启动时自定义组合键冲突且还没有收到过任何配置的 `ready`，则改用并持久化默认组合键；
默认组合键也冲突时停止回退，只保留托盘入口并明确报告，避免反复重启。
宿主每 500 ms 发心跳；异常退出时由 supervisor 重建并重新注册。主进程
执行健康判断前先消费子进程已经缓冲的输出，避免 GUI 短暂忙碌后误杀仍持续发心跳的宿主。空闲阶段
1.75 秒无活动或 4 秒无
启动握手时终止并重建；原生剪贴板读取使用独立的 10 秒硬超时，避免把合法的大数据内存复制按普通
心跳误杀。每代进程使用父进程生成的 nonce、严格递增事件号和 PID 握手，旧进程迟到消息不会进入
新代次。控制管道断开或父进程死亡时宿主直接退出，即使自己的 Win32 消息线程已经卡住也不会成为
孤儿进程。应用崩溃后若旧宿主尚未来得及释放会话 mutex，新代 supervisor 会按退避策略继续尝试，
不会把这次短暂占用误判为永久禁用；真正的 `RegisterHotKey` 组合键冲突才停止当前配置的重试。

macOS 后台使用 220 ms 定时器只读取 `NSPasteboard.changeCount`，变化时再读取 Qt MIME。Windows
主进程不再读取 `QClipboard.mimeData()`：剪贴板宿主使用 `AddClipboardFormatListener` 和
`GetClipboardSequenceNumber` 合并变化，通知后先等待 70 ms，再以 80/160/320/640/1000 ms 退避；
每次 `OpenClipboard` 都在 `finally` 中配对 `CloseClipboard`。文本、HDROP 文件、原生 PNG 与
CF_DIB/CF_DIBV5 在宿主中复制到私有 IPC 目录，短 JSON 管道只传原子 manifest 文件名。关闭系统剪贴板
后进入 materializing 阶段，由独立线程继续发心跳，避免 256 MiB 图片转换、写入和 `fsync` 被 1.75 秒
阈值误杀；该阶段仍有 120 秒硬上限。主进程后台校验目录、大小、协议、序号和图片尺寸后入库并删除
临时文件。所有 IPC 文件带 helper session 前缀，新代启动前会保留仍在消费的 session 并回收其他代次
遗留。若 `GetClipboardData` 因延迟渲染永久阻塞，只有剪贴板宿主被替换，Qt GUI 与热键宿主不受影响；
重建时从“最后成功消费序号”重放当前剪贴板。清空、暂停或写回时递增采集代次，已排队的旧 manifest
只能被清理，不能复活历史。

Windows 剪贴板宿主同时承担采集和发送，是系统剪贴板的唯一所有者；GUI 进程不调用
`QClipboard.mimeData()`，也不执行 Qt/OLE 写入。发送内容先在后台生成带 session/request ID 的原子
manifest：文本对应 `CF_UNICODETEXT`，文件对应 `CF_HDROP + Preferred DropEffect(COPY)`，图片对应
注册格式 `PNG`、`CF_DIBV5` 和保守的 `CF_DIB`。宿主在打开剪贴板前为全部格式分配
`GHND (GMEM_MOVEABLE | GMEM_ZEROINIT) HGLOBAL`，随后
`EmptyClipboard` 并按最有信息量的格式优先顺序用非空句柄调用 `SetClipboardData`；任一格式失败便
清空整个事务，未转移的句柄由宿主释放，成功转移的句柄归系统所有。该 eager 提交不依赖
`WM_RENDERFORMAT`、Qt 事件循环或拥有者进程继续存活。
为避免第三个位图格式把超大截图的双进程峰值推到 OOM 区间，原始 32-bit 位图像素统一受
128 MiB 总体入口上限约束；生成阶段直接读取 Qt 像素视图，避免额外复制一份完整 source buffer。

提交 ACK 不是“函数没有抛异常”，而是关闭剪贴板后先确认 sequence 相对写入前已前进，再验证 owner
是本代宿主窗口、`ClipSoon.InternalWrite` 的 request marker 一致且该类型所有格式可用。同一
request ID 的重放是幂等的。SelectionSender 在 ACK 前不隐藏面板、不恢复目标、不发送粘贴键；目标
激活并经过配置延迟后，宿主再次按 owner/marker/formats 验证同一事务。Windows 在为读取方合成兼容
格式时可能合法推进 sequence，因此验证会在新 sequence 上重新确认完整内容身份并返回实际稳定值，
不会把“序号变化”本身误判为覆盖；其他程序写入会失去 owner 或 marker，仍会失败。失败只允许重新
提交一次并再次校验，仍失败则取消自动粘贴。迟到、重复、错误 request/kind/session 或非法 sequence
的响应只能被丢弃，不能触发第二次粘贴。

Windows 的目标应用纯文本兼容复用同一个剪贴板宿主，但不进入 `SelectionSender`，也不模拟粘贴。
设置只保存经过校验、去重的绝对 `.exe` 路径；启用且至少存在一个目标时，主进程通过
`SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS)`
接收前台切换。进入目标后等待 80 ms 并重新核对 HWND 和进程路径，每次目标进入只请求一次。
宿主按请求携带的 clipboard sequence 读取 Unicode、CSV、HTML 或 legacy text 回退，在写入前再次
核对 sequence，然后以单一 `CF_UNICODETEXT + ClipSoon.InternalWrite` 事务提交。新复制导致 sequence
变化、非文本、文件/图片、私密格式和内部写入全部跳过；兼容请求不会抢占正在物化的外部采集，也不会
改变历史条目的最近排序或使用次数。

多选发送由 `ClipPanel` 一次性提交按当前可见行排序的不可变条目 tuple，应用层把整批交给
`SelectionSender.send_many()`；不得在 UI 信号处理中同步循环调用单项 `send()`，否则 `_busy` 门禁会
让首项之后的请求明确返回“已有发送任务正在进行，请稍候”，无法组成同一个批次。发送器冻结源 tuple
并在副作用前选择发送模式：同类文本映射为一个聚合 TEXT 单元，同类文件经过验证后映射为一个聚合
FILES 单元，同类图片放入保持顺序的可变 IMAGE 队列；任何混合类型直接拒绝。批次期间保持 busy，
并快照自动粘贴开关、目标身份、粘贴延迟和 `image_batch_interval_ms`；图片等待间隔默认 150 ms，
在设置层限制为 100–1000 ms。共享的 `_send_generation`
会在当前负载或异步阶段切换时推进，文件验证另由 `_validation_generation` 门禁，从而丢弃重复、迟到
或上一个阶段的回调。

两个及以上文本项按 tuple 顺序在内存中构造一个临时 TEXT 负载：Windows 使用 CRLF，其他平台使用
LF 连接原文本，不裁剪或规范化每项内容，也不额外添加末尾换行。正常路径只经历一次写入、ACK、目标
恢复、粘贴前验证和系统粘贴；这里写入的是字面换行，不模拟 Enter，避免聊天软件把 Enter 解释为发送。
关闭自动粘贴或没有原目标时仍只把完整合并负载复制一次。首次写入 ACK 后在一个数据库事务中调用
`mark_used_many()` 更新原条目，临时项不进入历史；随后失败时系统剪贴板仍保留完整合并文本，不存在部分 N/M 状态。
验证失败只允许重写同一个完整合并负载一次。

两个及以上 FILES 历史在后台逐记录串行完成 validation；全局最多保留两个尚未结束的验证任务，每条
验证最多 3 秒，整个文件批次共用 10 秒 deadline。每条结果都必须匹配仓库中的最新
`(id, kind, revision)`，任何确定失效项都会让整个计划在写剪贴板、隐藏面板和更新使用次数前停止。
全部通过后按 tuple 的记录顺序和记录内部路径顺序稳定扁平化，使用与平台文件负载一致的路径规范化键
去重并保留第一次出现的位置。去重后的路径数量受 `_MAX_FILE_BATCH_PATHS = 1_000` 产品上限约束；
1,001 个及以上在 write、面板 hide 和任何 `mark_used()` 前结束批次。通过上限检查后，还要在后台对
完整路径列表执行一次最终存在性复核，并再次 claim 每条 revision；最终复核发现失效路径时重跑仓库
validation，让既有 revision-CAS 清理规则移除对应历史。全部通过后生成且只生成一个临时 FILES 负载。
正常自动粘贴路径只执行一次 write、ACK、activate、verify 和 paste；关闭自动粘贴或没有原目标时只
复制一次完整文件列表。首次 ACK 后使用一次 `mark_used_many()` 原子更新全部源历史，临时聚合项不进入历史。

两个及以上 IMAGE 历史保持独立位图语义，不转为内部 PNG 路径、文件附件或合成图。预检要求自动粘贴
已开启、存在已捕获的原目标且数量不超过 20；任一条件不满足时零副作用拒绝。通过后按 tuple 顺序逐个
执行 write、ACK、目标身份核验、verify 和 paste；每张（包括最后一张）系统粘贴触发完成后按批次快照
中的 `image_batch_interval_ms` 预留有界消费时间，随后再次核对目标仍有效且当前负载未被覆盖。存在下一张时才继续覆盖；末图等待完成前
保持 busy，避免下一次发送立即覆盖。整个队列使用 60 秒阶段预算：每次开始新的 write/verify/paste/
settle 及收到异步回调时检查预算；已经在途的系统请求继续使用自身硬超时，返回后推进 generation、
释放 busy 并忽略更晚回调，避免提前释放 busy 后由旧请求覆盖下一次发送。该等待无法证明目标已实际消费。
该队列明确非原子：第一个失败点即使前面已有成功项也会停止剩余单元，并按已经完成粘贴触发的图片数
报告 `k/N`。检测到外部覆盖时保留外部新内容；若后续写入没有清空或替换剪贴板，则仍可保留最后一次
成功写入的图片。Windows 原生写入在 `EmptyClipboard` 后提交格式失败时可能无法恢复前一个负载，失败
状态不得声称旧图片仍被保留。
无论覆盖发生在当前图片首次粘贴前验证还是项间等待后的复核，图片队列都直接停止且不执行一次重写；
单项及聚合文本/文件继续保留既有的粘贴前一次完整重写策略。
每个图片单元独立关联自己的源条目，ACK 后只更新该条目一次，不能沿用聚合文本对整批 source IDs 的
计数方式。Windows 每张图片各自调用一次原生 `SendInput`，返回 4 只证明该张的四个按键事件进入系统
输入流，不能证明目标已消费，也不能把整个图片批次表述为原子成功。

文本、图片和文件之间的任意混合多选必须在写剪贴板、隐藏面板和更新使用次数前明确拒绝，不得猜测
转换为标题、路径、附件或合成图片。单条文本、图片和文件记录仍复用原有事务链路；单条文件记录即使
包含多个路径也继续作为一个 FILES 负载发送。所有发送计划只提交剪贴板负载和系统粘贴快捷键，绝不
模拟 Enter。

若采集外部剪贴板时 `GetClipboardData` 被延迟渲染永久阻塞，发送请求不会排在该调用之后：supervisor
终止旧宿主，在新 session 中用相同 request ID 重新准备并提交，最多尝试两代。进程级 10 秒原生操作
上限、请求级 22 秒 deadline 和粘贴前 5 秒 verify deadline 形成有界失败路径。标签构建的 Windows
冻结包 smoke 会真实发送文本、文件和图片，并在写入宿主退出后由独立 Win32 读取器验证 PNG、
CF_DIBV5 及直接提交的 CF_DIB 仍然存在；文本 ACK 与 verify 之间还会读取兼容格式，随后验证同一
事务。它还在独立、20 秒硬超时的 probe 进程中建立真实 Win32 面板、目标顶层窗口和子 EDIT，通过
冻结 EXE 的一次性焦点 helper 完成跨进程恢复，再由冻结 EXE 调用与主进程共享的 `SendInput`
实现向探针进程粘贴。文本与图片分支均 subclass 目标 EDIT，要求它实际收到 `WM_PASTE`；文本由
EDIT 所属 GUI 线程在默认粘贴处理完成后读取并逐字核对内容，图片则在消息到达时确认 PNG、
CF_DIBV5 与 CF_DIB 均可用，避免跨线程同步读取把空内容误报为窗口无响应。
focus/paste helper 的 smoke 与生产共用同一个 1.5 秒超时常量。目标消息线程为 daemon，退出消息与
join 结果均须验证。
sequence 确实前进的分支由 broker 状态机专项测试覆盖。

窗口弹出前，macOS 记录前台进程 PID，Windows 记录顶层窗口和实际焦点窗口的 HWND/TID/PID。
macOS 每次写入 pasteboard 时同时写入本次 request ID 的私有 MIME marker，并在 receipt 中记录写后
`changeCount`；首次 ACK 后只隐藏面板一次，等待可配置延迟并恢复目标，发送 `Cmd+V` 前必须同时核对
当前 `changeCount` 和 marker，避免批量图片期间把外部覆盖误当成本次负载。图片项间消费等待结束后还要
再次验证上一张 receipt，验证通过才允许写入下一张。Windows 恢复时先校验
目标与焦点 HWND 仍属于捕获的线程/进程和根窗口。普通 Win32 激活不足时，主进程启动一次性
`windows_focus_host`；只有该短生命进程会用 `AttachThreadInput` 临时连接当前前台、目标和焦点
线程，调用 `SetForegroundWindow + SetFocus`，在附加前后重复验证身份，逆序解除并检查每次结果，
随后立即退出。父进程用 1.5 秒硬超时等待并在 helper 退出后再次核验；因此 Qt GUI 线程不会被永久
绑定到外部输入队列，显式解除失败也由进程终止完成最终回收。若桌面客户端激活后异步重建编辑控件，
SelectionSender 在顶层身份不变时按 40/80/120 ms 有界重查前台 GUI queue；只有当前焦点仍位于原
根窗口且属于已捕获焦点进程才继续。随后按上述 ACK/verify 状态机，用一次原生 `SendInput` 批量提交
Ctrl-down、V-down、V-up、Ctrl-up 四个事件，返回值必须为 4 才报告“已触发粘贴”，部分提交会主动
释放按键并降级为“已复制”。`SendInput` 的返回值只证明事件进入系统输入流，不能替代 WeLink 对内容
实际出现的真机验收。Windows 只在 `IsIconic` 确认目标已最小化时调用 `SW_RESTORE`，普通或最大化
目标只置前并设为前台，避免自动粘贴改变用户的窗口尺寸状态。

Windows 的 Qt `activateWindow()` 不能保证把非活动应用带到前台，因此应用在 `show()` 后使用原生
窗口句柄请求 `SetForegroundWindow` 并验证结果。若普通请求失败，同一个一次性 focus helper 只在
面板仍可见且 HWND 仍属于 ClipSoon 主进程时临时连接输入队列；它不会调用 `ShowWindow`，命令有
1.5 秒硬超时，退出后主进程仍以 `GetForegroundWindow` 复核，成功才设置搜索框焦点。面板可见期间以
35 ms 定时器
读取 `GetForegroundWindow` 和鼠标主键状态：一旦面板曾成为前台，后续前台变化即隐藏；若系统始终
拒绝激活，则以前台基线变化或面板外首次鼠标按下作为隐藏兜底。模态窗口、应用弹出菜单及关闭
“失焦隐藏”时只同步按键边沿而不隐藏。该策略不安装额外全局鼠标钩子，也不吞掉目标窗口点击。
Windows 禁用 `ClipPanel.changeEvent()` 的通用 35 ms 失焦隐藏，避免它早于原生激活重试把刚显示的
面板隐藏；延迟激活带本次显示 generation，旧回调不能影响后一次显示。快捷键再次触发时，仅当面板
确实是原生前台窗口才切换为隐藏；可见但未获前台时会重新激活，而不是把用户看不到的窗口隐藏。

搜索框的 Enter 门禁只跟踪该控件收到的 `QInputMethodEvent.preeditString()`。输入法候选窗或
虚拟键盘处于可见状态不代表正在组字，因此不能使用 `QInputMethod.isVisible()` 阻止发送；只有
确实存在 preedit 文本时，当前 Enter 才交给输入法完成候选确认。

Windows 主面板和设置窗口保留普通、非分层的 Qt 顶层 backing store：不设置
`WA_TranslucentBackground`，不创建 Qt 透明分层窗口，从而绕过 Qt 的
`UpdateLayeredWindowIndirect` 分层窗口提交路径；同时不安装会扩大绘制脏区的顶层
`QGraphicsDropShadowEffect`。磨砂主题不请求 Windows DWM Desktop Acrylic，始终由应用内
`QPainter` 材质壳完成渲染。macOS 的无标题栏设置窗口在构造时固定透明 Qt 顶层模式，避免已显示窗口在磨砂和普通主题间
切换 backing store；普通深色/浅色由应用 `paintEvent` 绘制完全不透明的圆角根壳，避免原生浅色底从分区之间
露出。磨砂主题的历史列表滚动条由局部 QSS 绘制为
透明轨道上的窄拇指，避免平台默认的不透明轨道切开材质。QSS 使用 `pt` 字号，保证样式和 delegate 继承的
`QFont.pointSize()` 始终为正。跨平台视觉尺度由 `clipsoon.ui._UiMetrics` 集中管理：macOS/default
保留 Raycast/Spotlight 风格的 16/13 pt 层级，Windows 三个主题统一走 compact 指标，收紧搜索、
列表、设置、弹出层和默认面板尺寸，同时继续保留非分层 backing store 与应用内磨砂契约。
macOS 快捷键服务同时检查 pynput 的 `running` 与线程 `is_alive()`，应用每 2 秒检查并按 15 秒退避
重建；Windows 由独立 supervisor 以心跳主动替换失效子进程。Python 未处理异常写入轮转日志，
主进程原生崩溃由 `faulthandler` 写入 `native-crash.log`；helper 错误通过协议回传主日志，避免三个
进程并发轮转同一个文件。

用户级开机自启动由 `LaunchAtLoginManager` 隔离：macOS 原子写入
`~/Library/LaunchAgents/com.clipsoon.app.plist`，Windows 写入
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的 `ClipSoon` 字符串值。PyInstaller 环境只记录
当前应用可执行文件；源码环境记录当前虚拟环境解释器和 `-m clipsoon`，Windows 优先使用同目录
`pythonw.exe` 避免登录时出现控制台。设置保存失败时保留原设置值并反馈；已开启时每次应用启动
都会重写启动项，使应用升级或移动后的可执行路径得到刷新。

## 6. 性能路径

应用启动后常驻并预构建窗口、内存搜索索引和列表 delegate。热键呼出只记录前台目标、计算
当前屏幕位置并显示已经存在的窗口，不查数据库。搜索字段已归一化，列表由 `QListView` 虚拟
绘制；图片 PNG 编码、数据库写入、列表缩略图和右侧大图解码均放入 Qt 线程池。选中路径只同步
更新当前索引、背景和元信息，图片先显示加载占位，后台返回缩放后的 `QImage` 后才在 GUI 线程
转换为 `QPixmap`，并按路径和目标尺寸缓存。日志记录冷启动、呼出和超过 20 ms 的搜索，用于
回归定位。

可选状态记忆只保存在当前进程内：面板真正隐藏前以单调时钟记录类型 Tab、搜索词、稳定条目 ID
集合和当前焦点 ID，并启动单次到期计时器。时限内重显时先恢复类型、搜索词和过滤结果，再按
ID 恢复选择；到期时主动丢弃整个快照、恢复“全部”、清空搜索并把隐藏面板重置到完整列表第一项。持久化配置仍沿用
`remember_selection` 键以兼容 0.9.1 用户设置，但该开关的产品语义已扩展为完整面板状态。

主面板位置以 `panel_x`、`panel_y` 两个可选逻辑坐标写入同一 JSON 设置。首次运行仍按当前鼠标
屏幕居中偏上显示；用户只能从非交互空白区域开始拖动，释放鼠标且位置确实改变后才由面板信号
触发一次设置落盘。后续显示优先选择保存坐标所在屏幕，并按该屏幕可用区域约束完整窗口；旧屏幕
不存在时回退到当前鼠标屏幕，避免窗口留在不可见区域。

源码兼容与发布运行时是两层独立契约。`pyproject.toml` 接受标准版 CPython `>=3.11,<3.15`，
不包含 `3.13t`、`3.14t` 等 free-threaded（无 GIL）构建；兼容性 CI 在 Windows x64 与 macOS 15
arm64 上分别使用 CPython 3.11、3.12、3.13、3.14 安装源码并执行 Ruff 和离屏 pytest。该矩阵用于
验证一份源码，不代表发布四套 Python 运行时。正式 Release 的 canonical 打包解释器仍固定为
CPython 3.12，因此发布包内自带 3.12 运行时，最终用户无需安装 Python。本地开发者可以使用任一
受支持的标准解释器；若在 Windows 上以其他版本自行打包，one-dir 运行库名按构建解释器动态变为
`python311.dll`–`python314.dll`，构建检查不得写死 `python312.dll`。

开发验收统一通过仓库根目录的 `run.command` 或 `run.bat` 从当前源码启动。启动
脚本先终止本仓库的旧打包/源码实例，避免单实例锁让旧 `dist` 产物继续驻留并造成源码与界面
不一致。发布和最终包验收分别使用根目录的 `build_macos.command` 或 `build_windows.bat`；它们
转发到 `scripts/` 下的平台 PyInstaller 实现。

GitHub Actions 的 `.github/workflows/release.yml` 在推送 `v*` 标签时运行。Windows 任务固定使用 x64
托管 runner，macOS 任务固定使用 macOS 15 Apple Silicon runner，两个发布任务均固定安装 canonical
CPython 3.12；两者分别生成 ZIP 后作为独立
artifact 上传。发布任务只在两个平台构建均成功后运行，下载产物、生成 SHA-256 校验文件，
再使用最小的 `contents: write` 权限创建或更新对应的 GitHub Release。Windows 的 Ruff 与 pytest 验证拆分为
独立步骤；pytest 使用 `pytest-timeout` 的 90 秒单测边界、`-vv` 和 `--durations=20`，使潜在平台挂起可定位且
不会耗尽整个 30 分钟 job。对于同一 tag 的修正重推，发布并发组会取消旧运行，由新运行覆盖上传相同 Release 的资产。

界面主题由 `_style_sheet()` 提供基础颜色和字体层级。主题设置包含 `frosted`、`light` 与
`dark` 三种用户可选持久化值；默认 `frosted` 显示为“磨砂”，固定解析为浅色应用内磨砂材质，不随系统明暗或平台原生材质变化。`_FrostedSurface`
是主面板和确认弹出层唯一的自绘材质壳；macOS/Linux 的确认框根层仅作为透明的投影留白，不能在圆角确认卡之外再绘制不透明的矩形底；Windows 则保留普通非分层根窗口。磨砂材质以 `QPainter` 在圆角路径内
叠加受控环境色、半透明 veil、顶部 sheen、静态细线边框和 `QVariantAnimation` 驱动的局部、低对比度
指针 sheen；主面板不绘制流动光带、扩散环形光圈或点击脉冲，主材质壳内部保持不透明，底部和右侧信息区保持浅亮可读且不能透出下方窗口文字。主面板不再创建边框叠层控件，也不安装 `QGraphicsDropShadowEffect`；浅色、深色和磨砂主题统一由 `#card` 的 1 px 低对比度边框表达圆角外缘。非 Windows 顶层仅保留 1 px 抗锯齿边距，不再保留旧投影 gutter；Windows 继续使用普通非分层 backing store 和物理圆角 mask。由于 Windows `QRegion` mask 是二值裁剪、没有半透明边缘，Windows 顶层磨砂材质只负责不透明填充，不在 mask 边缘再绘制第二条描边；可见圆角边框只来自主卡片内侧的一根 1 px 细线，避免形成内外双线，同时不回到 Qt layered window 路径。旧设置文件中的已移除视觉效果键由 `JsonSettingsStore.load()` 的 dataclass allowlist 忽略，设置更新入口也过滤未知键，避免旧调用影响持久化。设置窗口在根层使用相同绘制函数，以应用内无标题栏头部提供标题，并在底部提供关闭与重置控件。该背景完全由应用生成，
不截取桌面、不需要屏幕录制权限。列表、详情和设置
分区是透明或低强调的功能层，搜索框是唯一允许的次级材质，避免多层玻璃卡片。磨砂主题与普通
主题共享静态细线边框；Windows 主面板不在顶层二值 mask 边缘描边，避免把 mask 台阶强化成外侧黑色圆角线。

列表 delegate 的选中与悬停状态共用蓝调、无描边的半透明填充：选中仅提高填充密度，浅色主题仍使用深色标题与图标，
悬停保持较低密度。这样当前项与指针预览属于同一材质系统，而不会形成“实心蓝色卡 + 白色描边玻璃卡”的双重语言。

主搜索框使用 16 pt，分类 Tab、历史列表、文本预览和信息区标题/标签/值统一使用 13 pt；搜索图标为 30 px，
仅通过鼠标打开设置，不争夺主面板输入焦点。面板激活时搜索框是唯一焦点 owner：列表、预览和放大镜均使用
`NoFocus`，任何平台控件仍尝试接管焦点时由下一事件循环在无模态/无弹出菜单条件下归还搜索框；上下键、修饰键
扩展选择和 Enter 批量发送仍从搜索框路由。搜索框以及设置窗口中实际承接输入的 `QLineEdit`（包括
`QKeySequenceEdit` 与 `QSpinBox` 的内部编辑器）会在 QSS polish 后显式把 QPalette 的
`Text`/`WindowText`、占位、选择和选中文字设为当前主题 token；应用级 `QProxyStyle` 仅对这些
显式标记的 `QLineEdit` 禁止原生插入光标绘制，再由应用按系统 `cursorFlashTime` 半周期绘制同一
主题 token 的闪烁竖线，因此透明/磨砂 backing store 不会在熄灭相位回退成白线。搜索框高度根据搜索文字的可见字形动态计算，使文字到输入区域顶部及
底部的距离均约为文字高度的一半；搜索、分类、内容和页脚之间用与列表/详情及预览/信息分栏共享 token 的 1 px 低对比规则划分。列表 delegate 使用 44 px 行高和 30 × 30 px 缩略图容器，继承列表字号并
只使用中等字重；`ClipListView` 在视口尺寸变化后主动重排 uniform-item 缓存，避免选中或悬停材质越过真实
可见宽度。无结果时 `QStackedWidget` 切换到语境化空状态并隐藏详情，恢复结果后返回列表。弹出层不能只依赖父窗口继承。
macOS 会把 `QComboBox` 的下拉视图放在独立顶层窗口中，应用主题与系统主题不一致时可能继续使用
系统背景；因此两个设置下拉框会直接为弹出视图设置 Base/Text/Highlight 调色板及普通、悬停、
选中、禁用 QSS。历史右键菜单也接收 ClipSoon 当前主题值，而不是再次从系统调色板推断深浅；
系统托盘菜单保持操作系统原生外观。自绘材质通过离屏 `QImage` 像素测试验证 rim、环境色差、局部交互 sheen
以及底部/右侧信息区的不透明度和浅亮度；自动化测试同时覆盖 Windows 非分层契约。


操作系统可能拒绝跨进程激活，目标软件也可能过滤带 injected 标记的键盘事件；此时不能把
“已复制”误报成“已粘贴”。应用保留剪贴板内容并给出降级提示。
